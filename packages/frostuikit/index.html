🧩 Widget Catalog & Detailed API Guide

1. 📝 Input Fields (AppTextField & Inputs)

Modern glassmorphic text input fields supporting pre-configured presets, automatic obscure text toggles for passwords, custom error feedback, and label support.

Supported Preset Variants (AppTextFieldType):

  • AppTextFieldType.email: Auto-configured with email keyboard, email icon, and validation.
  • AppTextFieldType.password: Auto-configured with obscure text mask and interactive eye toggle button.
  • AppTextFieldType.name: Auto-configured with word capitalization and person icon.
  • AppTextFieldType.phone: Auto-configured with numeric phone keypad.
  • AppTextFieldType.number: Auto-configured with numeric keypad.
  • AppTextFieldType.multiline: Text area supporting multiline input.
  • AppTextFieldType.text: Standard generic text field.

API & Key Parameters:

Parameter Type Default Description
type AppTextFieldType text Field preset variant controlling defaults.
label String? null Label text rendered above input box.
placeholder String? null Hint text displayed when field is empty.
controller TextEditingController? null Controller for managing text state.
obscureText bool? Auto for password Whether to mask text input.
prefix Widget? Auto based on type Leading icon or widget.
suffix Widget? Eye icon for password Trailing icon or widget.
validator FormFieldValidator<String>? null Validation function for Form state.

Code Usage Examples:

Email & Password Shortcuts via Mixin:
class LoginSampleWidget extends StatelessWidget with Inputs {
  final _emailController = TextEditingController();
  final _passwordController = TextEditingController();

  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        emailField(
          context: context,
          controller: _emailController,
          validator: (val) => val == null || val.isEmpty ? 'Required' : null,
        ),
        const SizedBox(height: 14),
        passwordField(
          context: context,
          controller: _passwordController,
        ),
      ],
    );
  }
}

2. 🧊 Glass Cards (BlurredCard & Cards)

Translucent glassmorphic container leveraging Flutter's BackdropFilter and ClipRRect to create realistic glass depth.

Smart Platform Optimization: BlurredCard automatically adapts to the platform for maximum performance: - iOS: Uses the highly optimized BackdropFilter (via Impeller) with a smooth sigmaX/Y: 5.0. - Android: Automatically falls back to Alpha Transparency (disableBlur = true) mimicking Telegram's approach for fluid performance on all devices. You can override this behavior by explicitly setting the disableBlur parameter.

API & Key Parameters:

Parameter Type Default Description
child Widget Required Child content inside the glass card.
borderRadius BorderRadiusGeometry? BorderRadius.circular(radius) Custom border radius geometry.
radius double? 50 Circular corner radius when borderRadius is omitted.
height double? null Explicit height for the container.
width double? null Explicit width for the container.
padding EdgeInsetsGeometry? null Inner padding surrounding child.
margin EdgeInsetsGeometry? null Outer margin around card box.
border BoxBorder? AppThemes.border Translucent border stroke decoration.
sigmaX double 5.0 Horizontal backdrop blur intensity.
sigmaY double 5.0 Vertical backdrop blur intensity.
clipBehavior Clip Clip.hardEdge Content clipping behavior (optimized for speed).
disableBlur bool? null (Auto) If true, disables the heavy blur filter and relies on alpha transparency. Defaults to true on Android and false on iOS.

Code Usage Example:

class CardSampleWidget extends StatelessWidget with Cards {
  @override
  Widget build(BuildContext context) {
    return blurredCard(
      context: context,
      padding: const EdgeInsets.all(16),
      child: const Text('Frosted Glass Container'),
    );
  }
}

3. 🔘 Action Buttons (AppButton, CircleButton, AppFloatingActionButton & Buttons)

For a concise entry point use FrostedButton.primary(label:, onPressed:), FrostedButton.secondary(label:, onPressed:), and FrostedIconButton(icon:, tooltip:, onPressed:). Constructors are const and need no BuildContext argument or mixin. Primary uses filled styling; secondary uses outlined styling. Null callbacks disable the button. isLoading blocks activation and displays progress; it does not automatically start a Future. Provide localized labels/tooltips from the host application. Optional icon, width, foreground/background colors and borderRadius allow common overrides. Icon actions support selection and an optional appearance override.

The short API delegates to the existing widgets, so theme, keyboard interaction and performance controls use the same implementation. AppButton, CircleButton and their helpers remain supported without new deprecations. Advanced blur/border/shadow customization remains on those existing APIs. Buttons Catalog demonstrates the short API alongside the original controls.

Circular buttons expose selected/enabled semantics and an accessible tap action. Their minimum layout target is 48 logical pixels. Disabled buttons do not animate on press, and reduced-motion settings suppress press scaling. Back helpers follow Directionality. Regression tests exercise keyboard activation, RTL, tooltips and disabled state. Light/dark geometry baselines are stored in test/goldens; Flutter's test font is used, so device typography still needs visual review. Run flutter test to compare baselines and review image changes before intentionally regenerating them with --update-goldens. A comprehensive set of action buttons supporting 5 visual style variants (AppButtonStyle). It also includes AppFloatingActionButton which acts as a versatile FAB (icon only, text only, or extended icon + text).

Button meaning is independent from appearance. Use FrostedActionRole.primary, secondary, or destructive on AppButton, or the matching FrostedButton constructor. Both examples retain destructive error colors:

FrostedButton.destructive(label: 'Delete', onPressed: deleteItem)
FrostedButton.destructive(
  label: 'Delete',
  style: AppButtonStyle.glass,
  onPressed: deleteItem,
)

Resolution order is: local color and border overrides, then the corresponding action colors in FrostedThemeData, then Material ColorScheme. Disabled content/surfaces use onSurface; focus, hover, and pressed overlays use the resolved role accent. Roles are also supported by icon buttons and FABs. Existing buttons default to the primary role.

For a normal Future-based action, FrostedAsyncButton owns the state cycle and does not require a controller:

FrostedAsyncButton(
  title: 'Save changes',
  icon: Icons.save_outlined,
  onPressed: () async => repository.save(),
  onSuccess: showSavedMessage,
  onError: (error, stackTrace) => logger.record(error, stackTrace),
)

Activation is blocked synchronously while an operation is active. Success and error feedback reset after feedbackDuration (1.2 seconds by default), or can remain visible with null. Late results after unmount are consumed without UI callbacks or state updates. Errors are delivered to onError; no Dialog or SnackBar is opened automatically. FrostLoadingButtonController remains the advanced API for manually controlled workflows.

Supported Style Variants (AppButtonStyle):

  • AppButtonStyle.glass: Translucent glassmorphic button with backdrop blur.
  • AppButtonStyle.colored: Solid primary accent filled button.
  • AppButtonStyle.outlined: Transparent button with primary border outline.
  • AppButtonStyle.text: Subtle text-only button without border or card fill.
  • AppButtonStyle.waterDrop: Lightweight liquid-highlight style for regular buttons and extended FABs.

FrostLoadingButton keeps its width during loading by default, uses a compact 24px indicator, and exposes configurable loadingLabel, successLabel, and errorLabel semantics. Set collapseOnLoading: true to opt into the older compact spinner layout.

The owner disposes its controller after removing the button. Listeners detach when the controller changes or the button unmounts. Call start() synchronously inside onPressed: live state checks block repeat taps before a rebuild. Non-idle states reject taps while preserving feedback colors. The button does not cancel application Futures; check mounted and invalidate stale requests on Reset, as demonstrated in Loading Button Catalog. The loading-dialog catalog is a dismissible preview with no delayed pop of an underlying route.

CircleButton now defaults to CircleButtonStyle.waterDrop and also supports the explicit glass and solid styles. The water-drop surface uses a small, performance-aware backdrop blur with a restrained highlight and rim. The old glass behavior remains available by setting style: CircleButtonStyle.glass. It uses lightweight gradients and highlights instead of a separate backdrop blur, making small icon buttons look like liquid droplets with lower GPU cost. The existing glass style remains the default.

circleButton(
  context: context,
  icon: Icons.settings,
  style: CircleButtonStyle.waterDrop,
  selected: true,
  selectedColor: Colors.deepPurple,
  selectedIconColor: Colors.white,
  tooltip: 'Settings',
  semanticLabel: 'Settings',
  onPressed: openSettings,
)

API & Key Parameters:

Parameter Type Default Description
title String? null Button label text string.
icon IconData? null Icon displayed beside title label.
style AppButtonStyle glass Visual style variant choice.
role FrostedActionRole primary Semantic action role and color family.
isLoading bool false Displays progress indicator when true.
isDisabled bool false Disables touch interactions and dims colors.
onPressed VoidCallback? null Tap callback handler.
height double? 48 Fixed button height.

Code Usage Examples:

class ButtonSampleWidget extends StatelessWidget with Buttons {
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        // Glass Button
        appButton(
          context: context,
          title: 'Glass Action',
          style: AppButtonStyle.glass,
          onPressed: () {},
        ),
        const SizedBox(height: 10),
        // Colored Button with Loading

3.1 🔄 Animated Loading Buttons (FrostLoadingButton)

A dynamic button wrapper built on AppButton that handles transitions between multiple states (idle, loading, success, error) using Lottie animations.

Available States (FrostLoadingButtonState):

  • idle: Displays the normal text and icon.
  • loading: Shrinks (or maintains width) to show an AppLoadingIndicator built with Lottie.
  • success: Shows a success icon with customizable success color.
  • error: Shows an error icon with customizable error color.

Code Usage Example:

class LoadingButtonSample extends StatelessWidget {
  final FrostLoadingButtonController controller = FrostLoadingButtonController();

  @override
  Widget build(BuildContext context) {
    return FrostLoadingButton(
      controller: controller,
      title: 'Submit Data',
      icon: Icons.upload,
      onPressed: () async {
        controller.start(); // Switch to loading
        await Future.delayed(const Duration(seconds: 2));
        controller.success(); // Switch to success
      },
    );
  }
}

6. 💬 Glassmorphic Dialogs (AppDialog & Dialogs)

Input dialogs submit through the same validation path from the confirmation button and keyboard Done action. Invalid input keeps the dialog open. Cancel returns null. AppDialog.actions provides an optional footer: on sufficient vertical space only the body scrolls, while very short viewports scroll the body and footer together. Keyboard insets are handled by Flutter's Dialog; callers should not add the keyboard height to insetPadding again.

The dialog regression suite covers a short viewport above the keyboard, RTL with 2x text scaling, portrait/landscape viewport changes, and keyboard insets appearing/disappearing. Input tests verify invalid Done submission, valid Done and button submission, Cancel, and system back results. These are widget simulations; physical-device keyboard behavior still benefits from manual checks. The Input Dialog catalog includes a longer description for trying these scenarios interactively.

Dialogs and bottom sheets share FrostedAdaptiveSurfaceLayout. Headers and actions remain visible on regular viewports, while short or keyboard-reduced layouts use one scroll view. FrostedAdaptiveActions stacks at narrow widths or accessibility text scale. Warning confirmations use FrostedActionRole.destructive when isDestructive is true. See FROSTED_ADAPTIVE_MODALS.md for compatibility and low-end-device behavior. See FROSTED_PERFORMANCE.md for the shared rendering policy, presets, and profile measurement protocol.

Glassmorphic popup dialogs designed to alert the user, ask for confirmation, or prompt for text input.

Available Mixin Methods:

  • showAppWarningDialog: Shows a warning dialog returning a boolean.
  • showAppErrorDialog: Shows an error dialog with an OK button.
  • showAppInputDialog: Shows an input dialog returning the submitted string, with support for validation.

Shared API & Key Parameters:

Parameter Type Default Description
context BuildContext Required Build context for navigator.
title String? null Optional header title string.
description String? null Optional description or body text.
icon IconData? Varies Optional top icon. Set to null to hide.
iconColor Color? error Theme color applied to the icon and its background.
confirmText String? localized Optional positive/submit label override.
cancelText String? localized Optional negative label override.
validator FormFieldValidator<String>? null Validation logic for showAppInputDialog.
titleColor Color? null Custom color for the title text.
descriptionColor Color? null Custom color for the description text.
confirmButtonColor Color? null Custom background color for the confirm button.
confirmTextColor Color? null Custom text color for the confirm button.
cancelButtonColor Color? null Custom background color for the cancel button.
cancelTextColor Color? null Custom text color for the cancel button.
isDestructive bool false Uses destructive styling for warning confirmation actions.

AppDialog now uses one clearer glass surface, a restrained blur, a fade/scale entrance animation, and a scrollable height constrained by the keyboard insets. Input dialogs move above the keyboard instead of being covered by it. The default cancel action is outlined while the primary action remains filled.

Code Usage Example:

          description: 'Please enter your full name below.',
          hintText: 'John Doe',
          validator: (val) => val == null || val.isEmpty ? 'Required' : null,

    );
  }
}

Scroll-to-hide app bar

Set appBarScrollBehavior: AppBarScrollBehavior.hideAll when a screen should reclaim the top edge while the user scrolls down. The default floating FrostedAppBar hides after hideAfter logical pixels and returns after showAfter logical pixels. The different thresholds prevent flickering when the user's finger changes direction. It also remains visible when the scroll position reaches the top. Reaching or bouncing at the bottom does not count as an upward reveal; the bar returns only after content actually moves upward away from the bottom edge.

The option is disabled by default and applies only to the default floating app bar. A custom appbar passed to BaseWidget continues to use the normal Scaffold.appBar behavior. The implementation changes state only when the visibility direction changes, keeps the scrollable child outside the animated app-bar subtree, and pauses app-bar animations while hidden. This avoids rebuilding the page content and limits extra work while the glass blur is moving.

Use AppBarScrollBehavior.collapseTitle to keep the back button and actions available while fading out only the title. This is useful on detail pages where navigation actions should remain reachable. The legacy hideAppBarOnScroll: true option is still supported and maps to hideAll.

BaseWidget(
  title: 'Messages',
  appBarScrollBehavior: AppBarScrollBehavior.hideAll,
  child: ListView.builder(
    itemCount: 50,
    itemBuilder: (context, index) => ListTile(title: Text('Message $index')),
  ),
)

}

class _StepperSampleWidgetState extends State<StepperSampleWidget> with Steppers {
  late FrostedStepperController _controller;

  @override
  void initState() {
    super.initState();

🎨 Central Theme Tokens (FrostedThemeData)

Import frosted_ui_kit.dart and install FrostedThemeData in ThemeData.extensions. Light/dark presets inherit colors from the matching Material ColorScheme instead of creating separate color schemes per widget.

final theme = ThemeData(
  extensions: const [FrostedThemeData(
    surfaceColor: Color(0xFFE6F0F4),
    contentColor: Color(0xFF172B36),
    borderColor: Color(0x55778899),
    buttonRadius: 20,
    dialogRadius: 28,
    glassBlur: 4,
    dialogBlur: 10,
    appBarBlur: 4,
    spacing: 12,
    motionDuration: Duration(milliseconds: 180),
  )],
);

Resolution: explicit local property, then theme token, then existing default. Generic cards inherit surface/border/radius/blur. Regular buttons inherit radius and foreground; water-drop surfaces inherit tint/blur. AppBar inherits blur, and Dialog inherits surface/opacity/radius/blur/spacing/entrance duration. Tabs and input fields inherit buttonRadius and their own blur tokens. Bottom sheets inherit surface tint, sheetBlur and dialogRadius + 4 for the top corners. Navigation inherits borderColor, navigationBlur and twice buttonRadius. Tabs use motionDuration for text and 1.25 times that duration for sliding feedback. A filled primary button still uses its ColorScheme primary. Local style overrides remain available; fixed functional measurements such as drag handles and icon sizes intentionally remain separate from design tokens.

Action roles can be customized independently from button appearance with primaryActionColor/onPrimaryActionColor, secondaryActionColor/onSecondaryActionColor, and destructiveActionColor/onDestructiveActionColor. Null role colors inherit the matching primary, secondary, or error pair from Material ColorScheme. The resolution order is local widget color, role token, then ColorScheme. Disabled colors derive from onSurface; interaction overlays derive from the resolved role accent.

Component blur defaults preserve existing appearances: inputBlur 10, tabsBlur 10, sheetBlur 15, navigationBlur 20. For a lighter recipe:

const FrostedThemeData(
  inputBlur: 4,
  tabsBlur: 4,
  sheetBlur: 8,
  navigationBlur: 6,
)

Instances are immutable and const defaults are reused. Lookup uses the normal Theme inherited dependency; no additional controller, timer or listener is created. lerp supports theme transitions with endpoint fast paths. copyWith retains nullable colors when omitted; construct a fresh instance to clear them. Blur performance settings remain independent of design tokens. No device FPS or GPU improvement is claimed without profiling.

Compatibility: constructor calls remain supported. BlurredCard.sigmaX/Y, FrostedAppBar.sigmaX/Y, and AppDialog.surfaceOpacity/blurSigma are now nullable overrides so an omitted value can inherit the theme. Code directly reading these public fields must handle null. Existing defaults and geometry goldens pass when no custom extension is installed.

The sigmaX/Y override fields and helper arguments on inputs, tabs and sheets are nullable too, to distinguish omitted values from explicit overrides. Their effective defaults are unchanged. Code reading these fields should resolve them against the matching token.

Verification: copyWith, lerp endpoints/interpolation, fallback, local surface override and button radius; complete widget/golden suite. Extend token coverage tests alongside further component migrations.

🔬 Shared Glass Rendering Architecture

All kit backdrop filters are built by the internal GlassBackdrop primitive. Cards and water-drop buttons retain their own tint, border, shadow and content layout; the primitive owns bounded clipping and blur only. No extra controller, timer, raster cache or unconditional RepaintBoundary is introduced.

FrostedPerformance is exported from the main library. Global blurEnabled and blurScale apply to all surfaces. Lite and zero scale create no backdrop filter. Cards retain their platform-specific Android fallback and local disableBlur; explicit colors are retained. Default card fallback uses fallbackOpacity in lite.

A private inherited marker prevents a nested kit surface from adding a second blur when an ancestor already filters its backdrop. This intentionally changes stacked glass: an input inside a glass dialog uses the dialog's blur, keeping its own tint and border. Nested stronger blur is not independently applied. Independent siblings keep separate filters; overlapping siblings are not given a shared BackdropKey, which could produce incorrect compositing.

Animated child content stays in its original layer order. Moving it or adding raster boundaries requires profile measurements, tracked in P1. Dialog entrance and button press scaling respect reduced-motion settings. Full animation policy for other components is outside this rendering refactor.

Tests verify ancestor filter reuse, independent siblings, lite and zero scale, balanced scaling once, and existing light/dark geometry goldens. These establish render-tree behavior and visual regression protection, not a measured FPS gain.

Adaptive Dialogs and Bottom Sheets

Dialogs and bottom sheets share FrostedAdaptiveSurfaceLayout, which divides a modal surface into optional header, scrollable body, and optional actions. This keeps behavior consistent across compact phones, tablets, large text, RTL, and keyboard-visible layouts.

Layout behavior

On a regular viewport the header and actions remain visible while only the body scrolls. When available height is too small, all three regions move into one scroll view. The threshold scales with accessibility text size so a large header or stacked actions cannot overflow.

FrostedAdaptiveActions displays secondary and primary actions in one row when space allows. Below 360 logical pixels, or at a text scale of 1.3 and above, the actions stack vertically with full-width touch targets. Secondary remains before primary, keeping the safe action ahead of a destructive action.

Dialog usage

AppDialog(
  header: Text(appStrings.deleteTitle),
  actions: FrostedAdaptiveActions(
    secondary: FrostedButton.secondary(
      label: appStrings.cancel,
      onPressed: cancel,
    ),
    primary: FrostedButton.destructive(
      label: appStrings.delete,
      onPressed: confirmDelete,
    ),
  ),
  child: Text(appStrings.deleteDescription),
)

showAppWarningDialog(isDestructive: true) assigns the destructive role to the confirmation action. Default Confirm, Cancel, Submit, and OK labels follow FrostedAppLocalizations when its delegate is installed. Explicit strings continue to take precedence.

Input dialogs retain one validation path for keyboard Done and the confirmation button. Dialog constraints continue to account for keyboard insets without adding them twice.

Bottom-sheet usage

showAppBottomSheet(
  context: context,
  title: appStrings.settings,
  actions: FrostedButton.primary(
    label: appStrings.save,
    onPressed: save,
  ),
  child: const SettingsForm(),
)

AppBottomSheet animates the complete surface above viewInsets.bottom instead of inserting a large empty spacer inside its content. Its height is clamped to the usable viewport through maxHeightFactor, which defaults to 0.92. header can replace the title row; showCloseButton, showDragHandle, and closeTooltip customize the default chrome.

Performance on lower-end devices

Each modal owns one BlurredCard surface. Nested kit controls detect the glass ancestor and do not create another backdrop blur. Bottom sheets use Clip.hardEdge by default, avoiding anti-aliased save layers for routine clipping.

All surfaces honor FrostedPerformance. In lite mode no BackdropFilter is created; the opaque fallback preserves contrast and geometry. Balanced mode scales sigma once. Keyboard padding uses the shared theme duration and becomes immediate when reduced motion is active. No FPS claim is made without profile-mode device measurements.

Compatibility

Existing child, title, sizing, glass, drag, and dismissal parameters remain supported. New header and actions parameters are additive. Existing custom dialog children continue to render, so applications can migrate incrementally.

Verification

Widget tests cover destructive roles, 320px width with 2x text, keyboard insets, a long bottom-sheet body, localized default actions, and blur counts in full and lite modes. Existing dialog validation, rotation, RTL, and keyboard tests remain part of the full suite.

FrostedAsyncButton

FrostedAsyncButton is the beginner-friendly API for a button that starts a Future. It owns loading, success, error, repeat-tap prevention, feedback timing, and mounted checks. No controller or setState is required.

Basic usage

FrostedAsyncButton(
  title: appStrings.save,
  icon: Icons.save_outlined,
  onPressed: () async => repository.save(),
  onSuccess: showSavedMessage,
  onError: (error, stackTrace) => logger.record(error, stackTrace),
)

The application supplies localized title, loadingLabel, successLabel, and errorLabel values when the defaults do not match its language.

State lifecycle

  1. The idle button accepts one activation.
  2. Its state changes to loading synchronously, before awaiting the callback. A second pointer, keyboard, or semantics activation is rejected.
  3. A completed Future shows success; a thrown error shows error and is passed to onError with its stack trace.
  4. The button returns to idle after feedbackDuration, which defaults to 1.2 seconds. Set it to null to retain the terminal state while the widget remains mounted.

The widget never opens a Dialog, SnackBar, or retry UI automatically. Those decisions remain in application code.

Lifecycle and late results

Disposing the widget cancels its feedback timer and invalidates the active operation generation. The application Future itself is not canceled because a generic Dart Future has no cancellation contract. When that Future completes after unmount, the result is consumed without setState, controller updates, or success/error callbacks.

For cancellable network work, cancellation remains the responsibility of the repository or request client. Pass its cancellation signal through the application callback.

Appearance and role

style controls appearance and role controls semantic colors, matching AppButton. A destructive asynchronous action can therefore use a glass surface without losing its error color family:

FrostedAsyncButton(
  title: appStrings.deleteAccount,
  role: FrostedActionRole.destructive,
  style: AppButtonStyle.glass,
  onPressed: accountRepository.delete,
)

Choosing the correct API

Need API
Run one Future and show automatic feedback FrostedAsyncButton
Application code drives every state manually FrostLoadingButton
Normal synchronous action FrostedButton or AppButton

FrostLoadingButtonController remains supported and is not deprecated.

Verification

Widget tests cover synchronous repeat blocking, success and automatic reset, captured errors and retry, disabled semantics, and completion after unmount. The full package test suite and flutter analyze must pass before release.

Authentication API Review

Current contract

The authentication module is generic at its domain boundary:

  • UserEntity carries app-specific attributes through customData.
  • AuthRepository is the application-facing contract.
  • AuthRemoteDataSource is an injectable backend adapter.
  • AuthController owns view state and can be supplied by the host app.
  • AuthScreen and AuthView expose flow flags and button overrides.

The data models and mock data source remain exported for 1.x compatibility and for package examples. Applications with a real backend should provide their own AuthRemoteDataSource and AuthRepository implementation.

Lifecycle correction

AuthScreen no longer creates a throwaway AuthController inside build. When no controller is supplied, AuthView creates exactly one local controller and disposes it with the view. When a controller is supplied, ownership stays with the caller.

This prevents duplicate listeners, unnecessary allocations, and state updates being sent to a controller different from the one rendering the forms.

Remaining follow-up

The controller currently contains default English feedback messages for the legacy standalone auth flow. A future major API can expose message builders or localized callbacks without changing the repository contract. Existing strings are retained for compatibility in the current release.

Frosted UI Kit Performance Policy

FrostedPerformance is the single performance policy for glass surfaces in frosted_ui_kit. It lets an application choose the rendering cost once at the root of a widget tree instead of configuring every component independently.

Presets

FrostedPerformance.fromData(
  data: FrostedPerformance.balanced,
  child: MaterialApp(home: const HomePage()),
)
Preset Backdrop blur Blur scale Recommended use
full Enabled 1.0 Flagship devices and desktop
balanced Enabled 0.5 General mobile default
lite Disabled 1.0 Low-end devices and reduced transparency

lite removes BackdropFilter entirely. It keeps the same layout, surface geometry, interaction, borders, and translucent fallback fill, so changing the policy does not cause a layout shift.

Component contract

Every shared glass surface must:

  1. Read FrostedPerformance.of(context).
  2. Skip BackdropFilter when blurEnabled is false.
  3. Multiply requested sigma values by blurScale exactly once.
  4. Preserve dimensions and decoration in all presets.
  5. Avoid nested filters through the shared GlassBackdrop scope.
  6. Keep clipping bounded to the surface shape.

On Android, BlurredCard also defaults to the lightweight alpha fallback unless the caller explicitly opts into blur with disableBlur: false. Explicit widget properties remain available for advanced cases, but the root performance policy always has the final ability to disable the filter.

Choosing a mode at runtime

Expose the policy as an application setting or derive it from a device-tier decision. Do not toggle it on every frame. A single inherited update rebuilds only the surfaces that depend on the policy:

class AppRoot extends StatelessWidget {
  const AppRoot({super.key, required this.mode});

  final FrostedPerformanceData mode;

  @override
  Widget build(BuildContext context) {
    return FrostedPerformance.fromData(
      data: mode,
      child: const MaterialApp(home: HomePage()),
    );
  }
}

Use lite when the platform requests reduced transparency, when sustained raster work is too high, or on low-end hardware. Use balanced before choosing full as the default for a broad mobile audience.

Measurement protocol

Performance claims must be made from profile builds, not debug mode:

flutter run --profile -d <device-id>
flutter drive --profile --no-dds -d <device-id> \
  --driver=test_driver/integration_test.dart \
  --target=integration_test/performance_test.dart

The repository includes a repeatable example scenario at example/integration_test/performance_test.dart. Run it from the example directory:

flutter drive --profile --no-dds -d <device-id> \
  --driver=test_driver/integration_test.dart \
  --target=integration_test/performance_test.dart

The test reports a catalog_scroll timeline suitable for comparing the same build with full, balanced, and lite. The app starts in balanced; change the Rendering Mode in Catalog settings and rerun the same scenario for the other modes.

Record the device model, OS, Flutter version, preset, screen, scroll scenario, and warm-up duration. Capture build time, raster time, frame timing, and jank. Compare the same scenario in full, balanced, android, and lite. This repository does not claim a fixed FPS or percentage improvement without those measurements.

For Android scrolling-heavy screens, the explicit android preset removes backdrop readback while preserving surface geometry, opacity, borders, and semantics:

Migration Guide

This guide describes the safe migration path for existing frosted_ui_kit applications. The 1.x compatibility policy keeps deprecated APIs available; migrations can therefore be applied incrementally.

Import boundary

Use the package entry point for application code:

import 'package:frosted_ui_kit/frosted_ui_kit.dart';

Do not import lib/src/... paths directly. They are implementation details and may change without preserving private structure.

Naming corrections

Replace legacy spellings when touching a file:

Before After
CricleButton CircleButton
BluredCard BlurredCard
bluredCard(...) blurredCard(...)
FrostedNavigationButtomBar FrostedNavigationBottomBar

The old names remain available in 1.x and have the same behavior.

Performance configuration

Wrap the application or a subtree in FrostedPerformance when you need an explicit rendering policy:

FrostedPerformance.fromData(
  data: FrostedPerformance.android,
  child: MaterialApp(home: MyHomePage()),
)

Use full for maximum glass fidelity, balanced for reduced blur, android for scrolling-heavy Android screens without backdrop readback, and lite for the lowest raster cost. Changing the preset does not change layout or semantics.

Buttons

Visual appearance and action meaning are independent. Keep destructive meaning explicit when changing button styles:

FrostedButton.destructive(
  label: 'Delete',
  onPressed: deleteItem,
)

Use FrostedAsyncButton for a Future-returning action when loading, success, error, repeat-tap prevention, and mounted checks should be managed by the widget. Keep FrostLoadingButtonController for manual state transitions.

Dialogs and bottom sheets

The shared adaptive surface layout now handles narrow screens, large text, keyboard insets, scrollable content, and destructive action emphasis. Existing dialog and bottom-sheet helpers remain source-compatible. Prefer the shared helpers over direct showDialog or showModalBottomSheet calls when adopting the kit's visual and accessibility behavior.

App bars and navigation

BaseWidget.hideAppBarOnScroll and appBarScrollBehavior are opt-in. Existing screens keep the previous always-visible app bar behavior unless a scroll mode is explicitly selected.

Release checklist

Before upgrading a production app:

  1. Run flutter analyze and the application test suite.
  2. Check RTL, large text, keyboard, and narrow-screen modal layouts.
  3. Run a profile scroll test on representative Android and iOS hardware.
  4. Replace deprecation warnings incrementally.
  5. Review CHANGELOG.md for visual or behavior changes in the target release.

Package Layout and Example Boundary

Package source

lib/frosted_ui_kit.dart is the supported public entry point. Reusable components live under lib/src/shared/widgets/, design-system utilities live under lib/src/utils/, and the generic authentication module follows the feature boundaries under lib/src/features/auth/.

The lib/main.dart file is retained only as a legacy package-local smoke-test harness. It is not exported and is not the recommended application entry point.

Interactive example

The example/ application is the canonical showcase. It owns the catalog screens, integration tests, profile performance scenario, and platform runner configuration. Package consumers should copy component usage from the example or the quick-start guide, not import files from lib/main.dart.

Dependency boundary

The package must not depend on its example. Example-only dependencies and test drivers stay under example/, while reusable code and public API tests stay in the package root.

Visual Consistency

The kit uses one surface language across cards, app bars, buttons, navigation, dialogs, and sheets:

  • translucent fills instead of opaque white panels;
  • shared rounded geometry and border treatment;
  • readable foreground contrast in light and dark themes;
  • explicit performance fallbacks on Android;
  • custom colors remain higher priority than defaults.

The default app-bar title uses the same translucent surface family as the water-drop controls. On Android, where the default card fallback skips BackdropFilter, this keeps the title from becoming a visually disconnected opaque panel. Applications can still override it with glassColor.

FrostedListTile adds a selected icon capsule, state-aware typography, and semantic selection metadata. AppSlidingTabs uses a bordered gradient pill with selected semantics, while FrostedStepper uses a lightweight gradient node and current-step emphasis instead of adding another backdrop filter. Stepper nodes also accept an optional stepBuilder for icons, images, Lottie, or any custom widget. The builder receives the step state and its content is constrained to the node size.

Visual regression checks cover both theme brightnesses. When changing surface tokens, verify the catalog on Android and iOS and rerun the profile scroll scenario before changing the default appearance.
